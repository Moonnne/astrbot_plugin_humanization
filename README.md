# Humanization

<img src="logo.png" alt="Humanization" width="128" />

AstrBot 群聊内容感知与回复控制插件，作者 **Moonne**，版本 **v0.1.2**。

仓库：https://github.com/Moonnne/astrbot_plugin_humanization

插件图标为根目录的 `logo.png`，随代码提交。AstrBot 自动读取该文件并设置插件图标，无需在 `metadata.yaml` 增加自定义图标字段。

## 支持范围

- AstrBot `>=4.28.1,<5`，本地 Agent Runner。4.28.1 是所用原生请求收集接口的起始发布版本。
- aiocqhttp / OneBot v11，例如 NapCat 和 SonwLuma。
- 群聊整体感知、私聊独立感知。未唤醒主模型的普通消息也可记录。
- 默认不启用任何会话。插件不会自动改动宿主人格、模型或实际群聊配置。

## 配置与启用

1. 在 AstrBot 插件配置中打开 Humanization。
2. 在“会话启用范围”多选已知会话，或填写补充 UMO。选择“全部会话”可覆盖所有 OneBot 会话。
3. 整个群使用 `[平台实例]:GroupMessage:[群号]`，私聊使用 `[平台实例]:FriendMessage:[用户号]`。方括号内为占位符，填写时替换为实际值，不输入方括号，例如 `onebot:GroupMessage:123456`。平台实例不是固定的 `aiocqhttp` 字符串；可通过 `/sid` 查看实际 UMO。即使启用了群内成员隔离，选择整个群仍使用群号。
4. 在 Recorder 和 Controller 开关下方分别选择摘要模型和参与门控模型。主回复模型沿用当前 AstrBot 会话模型。
5. 在 Controller 顶部填写机器人名称和别名，选择工作模式；按需要调整积极度、提示词和主动发言开关，保存后插件热重载。

会话选择框使用宿主已有的会话名称，启动／重载时更新；未显示的会话可手动补充。开启“全部会话”时，两项范围输入使用官方条件显示机制隐藏，原有选择保留。官方多选下拉框目前不支持输入新选项，因此仍需使用补充 UMO 列表。空范围不记录、不总结、不代理。Controller 关闭时只记录，宿主继续按原规则回复；Recorder 关闭时停止全部接管。

未选摘要模型时只记录原始消息。未选门控模型时普通消息保持安静；默认开启的“@ 必回复”仍可直接请求主模型，群聊须先达到最低上下文要求，私聊不受此门槛限制。主模型或平台不可用时不保证送达。

“群聊最低上下文”默认开启，默认 50 条。机器人先旁听，只有当前群在 Recorder 的 `messages` 表中实际保留至少 N 条记录后，才允许 Controller 规划和主模型回复。私聊跳过此门槛。直接沿用 Recorder 的入库过滤和去重，不另设累计计数；已记录的机器人气泡也计入，被过滤或滚动删除的消息不计。群成员共用整个群的记录。条数须为 1 至保留条数之间的整数；默认保留 500 条、门槛 50 条时，正常滚动不会跌回门槛以下。

群聊观察期间仍记录消息、异步整理日记，管理指令照常执行；群聊的 @／提及必回复及空闲主动发言也受门槛限制。达到门槛只允许正常调度和判断，不强制立即发言，不等待摘要模型完成。本限制与模型读取窗口独立；修改门槛不会让模型每次读取 N 条。群聊数据重置后重新检查；重载沿用已有数据库记录。

AstrBot 自定义规则中只关闭“启用 LLM”时，Controller 规划和主模型回复停止，Recorder 仍记录；已配置摘要模型时仍可独立调用它整理日记。若希望停止辅助摘要调用，可清空摘要模型选择。关闭整个会话的“消息处理”会在宿主前置阶段阻止事件进入插件，因此无法继续记录。

## 回复规则

- 命令插件照常执行，Humanization 不接管命令回复。
- “过滤指令模式对话”默认开启，统一控制插件数据库入库、观察上下文和主模型输入。已识别指令及指定前缀消息不入库、不计摘要、不进入门控；命令插件正常执行，其输出不作为本插件的角色发言记录。关闭后可记录指令输入，主模型也可读取原生指令历史。
- “额外指令前缀”可填写多个值，默认 `/`。开启过滤后，匹配的未注册指令也不会回落到默认 LLM。已存原始输入会按当前前缀筛选，不交给门控、新摘要或主模型观察；原记录不因此删除。
- 开启过滤时，在原生 Agent 开始钩子中临时取出可按前缀识别的指令回合（连同其回复、工具消息），结束钩子中恢复，随后交由原生历史保存；指令引用也会过滤。不会因过滤删除原生指令记录，不额外调用模型或增设数据库写入；本轮临时引用在结束、异常或取消后释放。普通聊天继续使用宿主压缩，已经被压缩的普通内容不会复原；旧定位消息被压缩时，指令记录放到下一条仍保留的原消息前。原生完整群消息记录及其查询工具不受该选项控制。
- 历史消息没有指令前缀时无法可靠识别；已有日记不自动重写，原生历史是否记录指令插件的输出仍由宿主及该插件决定。
- “机器人名称”默认 `Bot`，与“别名”共用提及识别，并以稳定身份信息注入 Controller 系统提示词。英文名称忽略大小写并检查单词边界，中文名称按文本包含识别。不会自动改写主模型的人格。
- “@ 必回复”默认开启，“提及必回复”默认关闭。群聊达到最低上下文要求后，命中时绕过普通调度、抽样和普通冷却，但仍调用 Controller 规划情绪与表达，并要求 reply=true；规划未配置、超时或输出非法时仍交给主模型自行表达，不虚构情绪。仍遵守宿主权限及输出协议；私聊不检查最低上下文。必回复表示提交主模型，不要求角色接受用户任务；两个开关与提及积极度下限独立。
- 未开启必回复时，@ 或名称提及使用积极度下限：`A_effective = max(当前时段积极度, 对应提及下限)`，同时命中时使用 @ 分支。下限为 1 仍需语义判断；关闭必回复并将积极度及提及下限均设为 0 才是完全静默。
- 积极度表示进入语义判断的频率。消息调度与概率抽样都不能保证实际发言比例，门控模型可以继续选择安静。
- 支持多个群聊／私聊积极度时段。使用配置时区；开始时刻包含，结束时刻不包含。跨午夜有效；相同起止表示全天，重叠时段会拒绝加载并在日志说明。
- 同群共享回复锁和调度状态，保留触发消息的原 UMO，私聊按发送者隔离。其他插件已经发送回复时，本插件不再接话。
- 原生 Agent 保留当前人格、工具和会话历史；辅助人格片段只取提示正文。可配置工具禁用名单，从已有权限中进一步移除工具。

Controller 与 Recorder 使用独立的单次模型调用，不维护辅助 LLM 聊天 session，不自动套用原生 Agent 上下文压缩。Controller 输入包含固定协议、机器人名称／别名、行为与群聊／私聊设定、观察消息、跨日期话题、最近有效决策及本轮时间和触发信息。不自动复制主模型人格、原生对话历史或工具列表；角色关键倾向需在 Controller 的行为设定中说明。

Controller 输出严格 JSON：恰好包含 `reply`、`reason`、`emotion`、`plan`。沉默时仍报告情绪，`plan=null`；回复时规划参与方式、语义焦点、交互意图、表达风格及回复指导。14 个一级情绪是项目自定义分类，强度为 0—3；风格与情绪独立。reason 最多 80 字符、guidance 最多 300 字符、完整 JSON 最多 4096 字符；不接受额外字段、代码围栏、错误类型或不可见的消息／话题 ID，不裁切、不修补格式。普通失败保持安静；必回复失败保留主模型入口。这些是接收校验上限，不是服务商生成 Token 上限。

Controller 默认观察 30 条消息（与主模型共用条数设置），独立读取最近更新的 30 个话题候选，跨日期不限两天；`context_topics=0` 禁用话题读取，`topic_context_chars` 默认 12000，按完整条目共享字符预算，超预算跳过并明确省略数量。Recorder 和主模型的常规日记预算仍独立。程序提供当前时区时间、距最近消息和发言的时长，不让模型填写时间。

`controller_decisions` 每个会话保留最近 10 条有效规划，包括不回复的决定；重启保留，`reset_data all`、`reset_data today` 和全量清理都会删除对应记录。输入只投影旧情绪、结论、时间、焦点及执行状态，不重复旧 guidance。只在实际模型评估成功时更新，不增加情绪轮询；抽样、冷却和模型异常不伪造情绪。模型结合真实间隔和新刺激决定延续或减弱情绪，不使用固定衰减公式。

规划与发送结果分开保存：`observed` 表示决定沉默；`pending` 为等待执行；`processed` 为原生发送阶段完成，非送达／已读确认；另有 `unconfirmed`、`failed`、`superseded`。重启后遗留 pending 标为 unconfirmed。主模型仅临时接收本轮情绪、计划和必要的焦点消息／话题快照，不复制全部决策历史。语义焦点不会改变会话路由，也不自动调用 QQ 引用接口。

辅助请求使用紧凑 JSON，不把 JSON 观察资料再次转义成字符串；摘要将重叠消息放在新增消息之前，已有日记放在消息之后，减少易变字段对前缀复用的影响。消息窗口滚动、日记变化、服务商缓存期限等仍会影响命中，不保证固定命中率。默认 Controller 和主模型观察 30 条、摘要每新增 100 条用户消息触发一次、单次最多读取 200 条；字符预算不等于 Token 上限。

## Controller 工作模式

Controller 默认使用“消息调度模式”，也可选择“概率抽样模式”。概率模式对每次候选消息使用 `R < A_effective` 判断是否进入语义门控，仍受普通冷却与连续消息合并控制。必回复由独立开关决定。

配置页只显示所选模式的专属参数：调度最短／最长补偿等待仅在消息调度模式显示。积极度、时段、提及下限、冷却和合并等待由两种模式共用；概率模式没有额外专属参数。使用官方 `condition` 显示机制，隐藏配置保留原值。未满最低上下文门槛的群聊输入不积累调度额度，私聊不受此门槛限制。

“消息调度模式”对每条成功入库的真人消息累加额度 `C += A_effective`，达到 1 即安排一次评估，保留小数部分，不累积多个模型请求。额度用标准库 Decimal 累加，0.1 的第十条消息可准确满足额度；0.8 平均约每 1.25 条评估一次。指令、重复消息和自身消息不计数。

达到额度后等待合并窗口。额度不足但有新消息时，使用有限等待 `W(A) = W_min + (W_max - W_min) × (1-A)²`，默认最短 5 秒、最长 60 秒；积极度 0 不补偿。持续聊天的合并等待也受这一期限约束；普通冷却和退避可能延长实际等待。普通名称提及／@ 会加快到合并窗口，但仍经过语义门控。

| 积极度 | 无合并时名义评估间隔 | 默认低流量补偿 |
| --- | --- | --- |
| 1 | 每条 | 通常只等合并窗口 |
| 0.8 | 平均约 1.25 条 | 约 7 秒 |
| 0.5 | 平均约 2 条 | 约 19 秒 |
| 0.2 | 平均约 5 条 | 约 40 秒 |
| 0.1 | 平均约 10 条 | 约 50 秒 |
| 0 | 普通消息不评估 | 不补偿 |

配置页提示当前默认群聊／私聊及各时段的估计频率，保存重载并重新打开配置页后更新；官方控件不支持实时计算提示。这是评估频率估计，实际发言还受门控、冷却、合并及退避影响，必回复另计。

同一批消息在 reply、wait、调用异常或宿主丢弃后消费一次评估机会，无新输入不反复请求。连续第二次语义 wait 开始采用 10、20、40、80、120 秒封顶退避，原生发送完成后清除；必回复绕过退避。执行中的新消息保留为下一批，观察范围使用提交时的序号截止点，旧回合不会误消费新消息。

每群／私聊最多一个待评估请求和一个有效计时器，批次执行时的新消息只保留一个待处理快照。必回复清理对应普通批次；若执行中又收到多个必回复，合并到最新一次明确提及的快照。重置、重载、卸载会取消计时器、清理快照并拒绝旧代际事件，不从已有数据库历史补发。

到评估时点，将带专用标记、保留真实输入和原 UMO 的事件送入原生队列；前置处理器阻止其重复执行其他消息插件和原生入站记录。主模型继续经过原生 Agent、工具循环、历史、统计及发送阶段。本轮媒体临时文件由调度快照接管并在结束后释放。调度事件会再次经过宿主的前置检查，严格限流可能额外消耗一次额度并延后或丢弃回复，不绕过宿主限流。

## 主动发言

主动发言默认关闭，需要单独启用，且对应群必须整体在范围内。默认无人聊天 60 分钟后可评估；评估间隔 15 分钟；距机器人上次发言至少 4 小时；每天最多主动开话题 2 次。

概率模式使用“当前时段群聊积极度 × 主动评估系数”抽样；消息调度模式在每次合法空闲检查时累加该乘积，额度满 1 才评估。两种模式都仍需模型判断，积极度 0 不主动发言。23:00—08:00 默认不主动发言。主动发言后无人回应时不会继续追发。新消息（包括被过滤的指令）会使过时的空闲意图失效。

主动事件经过宿主 Pipeline，并使用群公共 UMO 和非管理员调度身份，不借用某位成员的隔离历史或权限。平台发送只使用目标群路由。仍遵守群的宿主会话、LLM、插件开关和白名单。

## 数据与日记

数据位于 AstrBot 插件数据目录的 `chat/db/chat.sqlite3`，与源码分离。固定表：`sessions`、`messages`、`diary_days`、`diary_topics`、`reply_runs`、`controller_decisions`。

数据文件仍是同一个 `chat.sqlite3`，新话题表和规划记录表都在其中。`-wal` 保存尚未 checkpoint 回主文件的已提交变更，`-shm` 是 WAL 的共享索引；两者属于 SQLite 管理的辅助文件，不能直接删除。

数据库由 `utils/database.py` 统一管理：一个串行写连接、两个可复用的只读连接。写事务包含去重、计数、裁剪或日记与游标等成组变更，失败／提交前取消时回滚；查询使用独立读快照，不看到其他事务未提交的数据。事务内只处理数据库工作，不持有连接等待 LLM。卸载／重载先停止后台任务和回复任务，再拒绝新数据库操作、等待已受理操作结束、关闭读连接，执行 `wal_checkpoint(TRUNCATE)` 并关闭写连接。普通模式在 AstrBot 日志回显 `database.checkpoint`，调试模式遵循现有日志分流。

运行时保留 1000 页的自动 checkpoint，配置 `journal_size_limit=4194304` 限制 WAL 重置后保留的空间；它不是 WAL 的硬性大小上限。正常关闭且没有外部连接占用时，SQLite 会整理并移除辅助文件；外部读事务阻挡时记录 `busy` 状态并保留 WAL，异常退出也不能保证立即整理。此过程不执行耗时的 `VACUUM`，不会承诺删除记录后主文件立即缩小。参见 [SQLite WAL 说明](https://www.sqlite.org/wal.html) 和 [checkpoint 参数](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint)。

代码职责分为三层：

- `models/`：消息、会话重置目标、Controller 决策、时段配置、调度状态及发送结果等数据模型。
- `core/recorder/storage.py`：业务存取与事务组合。Runtime、Recorder、Controller 和管理指令调用它提供的查询／写入方法。
- `utils/database.py`：连接池、事务与生命周期；`database_session.py`：游标操作与取消收尾；`sql_queries.py`：加载命名 SQL。

所有运行 SQL 位于 `resource/sql/`：`schema.sql` 建表，`connection.sql` 配置连接和 checkpoint，其余按会话、消息、日记日期、日记话题、回复记录、Controller 决策分类。每条 SQL 以 `-- name: 名称` 标识，运行时按 `文件名.名称` 读取，用户输入仍通过参数绑定传入。该目录是必需运行资源，应随插件上传 Git。测试用 SQL 仅用于隔离数据库的验证与故障注入。


- 每个群／私聊默认保留最近 500 条，包括完成原生发送阶段的机器人气泡。
- 默认每新增 100 条真人消息触发总结，每次最多观察 200 条。须满足 `触发条数 <= 窗口 <= 保留条数`。
- 保留原 UMO、平台实例、机器人身份、群号、发送者、发送与接收时间、消息 ID 和消息文本／消息段类型。图片、视频和文件只记录 `[image]`、`[video]`、`[file]` 等类型标签，不记录资源地址或内容；本轮主模型媒体处理交给宿主。
- 摘要按未处理游标追赶，利用已处理消息的重叠窗口衔接；失败不推进游标。超过保留窗口的积压会明确标注覆盖缺口。
- 日记使用 `diary_days` 每日索引和 `diary_topics` 话题条目两张固定表。每个会话按日期组织日记，每个话题独立保存主题、用户行为、我的行为、用户反应及来源序号范围；程序渲染日期标题和五个阅读标签，不存重复的整篇正文。
- Recorder 只输出 JSON 话题变更：新增条目或按 ID 局部更新当日条目，未涉及的条目和字段保留原值。输入包含按插件时区格式化的消息时间，话题时间取新增条目所引用的最早消息序号，后续更新保留原时间。字段分类不代表行为先后顺序。
- 每项变更必须引用本轮提供的消息，且包含新增消息证据；只能更新本轮展示的、属于当前会话当日的条目，同一条目一次只能更新一项。无有效内容返回空变更列表，正常推进总结游标。条目变更、每日状态及总结游标在一个事务内提交，失败不部分保存。
- 当天可更新，历史封存不可改写。跨日未总结的消息在整理当天补记，历史错误在当天更正；实际话题时间保留原日期。日记不再按每日字符上限裁剪，持续保存到管理员清理；来源序号用于溯源定位，不保证滚动删除的原消息仍可查询。
- Recorder 和主模型选取最近两个有话题或缺口记录的日期参与上下文：优先最近日期及最近更新的话题，在 `diary_context_chars`（默认 2400）预算内选择完整条目，展示时恢复时间顺序。此预算计算话题结构／文本长度，日期、省略提示等元数据另计。省略的话题仍在数据库中；有限上下文下可能出现重复续记，不做语义去重。
- `summary_output_chars`（默认 6000）限制单次完整变更 JSON 长度，超限或格式错误时整批失败，后台后续重试，不裁切输出。这两个配置替代原 `summary_chars`，不限制每日累计存储长度。
- Controller 按独立的最近话题数量和字符预算读取跨日期的结构化条目；主模型读取程序生成的可读日记；Recorder 读取带 ID 的结构化条目，历史日期仅作参考。最近日记与观察窗口临时注入主模型，不重复写入 AstrBot 对话历史；不使用向量库或嵌入模型。
- `[Coverage]` 表示原始消息滚动缺失或本次输入内容被截断；`[Context]` 表示已保存但受预算限制未展示的话题，不是数据丢失。
- 当前未发布版本按全新数据库结构实现，不迁移旧测试数据。升级测试实例前请停止插件并自行备份或丢弃旧测试数据库，再加载插件；程序不会自动清理旧数据或将旧整篇日记转换成条目。
- 配置保存重载后扫描消息库，按新保留条数裁剪。只删除数据库中的过期行，不删除数据库文件。
- 回复日志最多 1000 条。`processed` 表示收到原生发送后钩子，`unconfirmed` 表示气泡没有完成通知，`filtered` 表示正文被过滤；中断标记为 `unknown`，不自动重发。宿主会捕获部分发送异常，因此完成通知不等于每段发送成功或对方已读。

## 提示词与输出

行为、表达、群聊和私聊文本的默认内容存放在 `_conf_schema.json`，直接显示在官方文本框中，可基于默认内容修改，也可选择 AstrBot 人格正文覆盖。留空并保存重载会恢复默认文本。主人格仍使用 AstrBot 当前人格；Controller 的名称／别名不会自动写入主人格，需要在主人格中说明角色接受的称呼。

若叶睦的最新可选人格与风格示例位于 `docs/U3.md`，适配结构化情绪规划和话题日记；`docs/U2.md` 保留原文。示例需手动配置，不会自动覆盖当前人格。

`resource/prompts/` 仅保留门控决策、摘要和输出格式三个内部协议文本（`gate.txt`、`summary.txt`、`output.txt`），插件运行需要这些文件，应随代码提交到 Git。四份可编辑默认文本无需另外保存副本；保留 `resource/` 目录。

输出协议固定为单行正文，以 `$` 分隔 1—3 个气泡，不按普通标点拆分。最终回复采用非流式校验；格式不合规时最多调用主模型修复一次。再次失败则不发送。无法通过语法解析精确识别所有自然语言舞台描写，语义约束仍依赖模型。

Humanization 只缓存本轮最终正文，等原生 Agent 完成工具循环、统计和历史保存后，逐个 `yield` 气泡。每个气泡继续经过宿主内容检查、回复前缀、文转图、TTS、自动引用、原生分段和发送后钩子，插件不直接发送最终正文。协议约束生成的台词，不约束宿主装饰后的文字／语音／图片；原生分段仍可能将一个气泡拆成多条实际消息。

缓存只存在本轮事件的内存中，完成、异常、取消或生成器关闭时清除，不创建额外缓存文件。格式修复失败只过滤正文，保留媒体，并继续 Agent 收尾；不会为格式错误停止整轮事件。工具状态、工具直接发送、一般错误通知和其他插件发送保留各自原生流程，不按角色正文解析。

Recorder 通过原生发送后钩子记录宿主装饰后的消息，媒体仅保留类型标签。为保留宿主取出单独发送的语音段，返回的消息结果继承原生结果类型，并观察其 `derive()` 创建的发送消息链；不替换宿主发送方法。

## 日志与调试模式

“日志设置”位于插件配置末尾的“危险操作区”之前。“启用调试模式”默认关闭；`runtime.log` 大小上限默认 5 MB，`dev.log` 默认 10 MB。单位按 1 MB = 1024 × 1024 字节计算，允许非负小数，0 表示无限制。两份文件都按 UTF-8 实际字节数滚动，保留最新的完整 JSON 行，不截断中文或日志正文。保存重载后生效，也会裁剪已有的超限文件；增大上限不会恢复旧记录。单条日志本身大于文件上限时跳过该条，避免破坏 JSON 或清空其他记录。

文件位于插件数据目录的 `log/runtime.log` 和 `log/dev.log`，采用 UTF-8／CRLF，每条日志为一行 JSON；换行正文及堆栈在 JSON 字段中转义。

| 模式 | 本插件控制台日志 | runtime.log | dev.log |
| --- | --- | --- | --- |
| 普通 | 核心操作与异常类型；模型用量摘要不输出 | 核心记录及模型用量摘要，按容量滚动 | 不新增 |
| 调试 | 不输出 | 每次模型用量摘要，按容量滚动 | 全部核心、用量及调试记录，按容量滚动 |

核心记录覆盖初始化、上下文整理、摘要开始／完成、门控规划结果、回复开始／结果与关闭；不附加原始聊天、日记正文、完整提示词或凭据。调试记录覆盖配置、消息筛选、抽样与门控、上下文、模型请求／响应、工具参数／结果、数据库查询与提交、输出修复、原生发送完成及异常堆栈，带回合或关联编号。

Recorder 完成时输出 `summary.complete`：会话 UMO、实际新增整理条数 `message_count`、包含重叠资料的模型输入条数 `context_count`、`duration_seconds` 以及新增／更新话题数 `added_topics`／`updated_topics`。报错时输出 `summary.failed`：会话、耗时、错误类型、成功提交条数 0 及本批候选条数；候选数不代表实际模型输入条数。只有日记成功保存后才报告完成，失败仍保留原游标。群聊日志使用整个群的 UMO，私聊使用对应私聊 UMO，方便定位。

Controller 模型完成后输出 `gate.complete`：会话、`reply`／`wait` 决定、主情绪 `emotion`、强度 `intensity`、参与方式 `participation` 和耗时；普通日志不输出 reason、guidance 或聊天正文。完整规划仅在调试日志中记录。失败输出 `gate.failed`、会话、耗时和错误类型：普通消息保持安静，必回复继续交给主模型。无模型配置的兜底或算法跳过分支不伪造模型规划。普通模式输出到 AstrBot 控制台与 runtime.log，调试模式只写 dev.log；Token／缓存统计仍只写文件。

每次 Controller、Recorder 和格式修复调用均写入 `model.usage`，不依赖调试开关、不打印到 AstrBot 控制台；调试模式下 dev.log 同时保留这份摘要和原有详细请求／响应。`purpose` 区分 `controller`、`recorder`、`format_repair`、`main`，`trace` 关联原有回合；摘要不包含提示词、聊天正文、回复正文或凭据。

摘要包含 `estimated_input`（AstrBot 原生启发式估计）、`usage.input`、`usage.input_cached`、`usage.output`、`usage.total`、`cache_ratio`（0—1）、提供商 ID、响应 ID、调用状态和辅助调用耗时。Token 估计不含工具 schema 的开销，不是计费依据。`provider_details` 仅提取原始用量中的已知数值字段，包含提供商返回的缓存读写、未命中或推理数量；显式缓存数量优先于宿主未映射的缓存字段，`cache_source` 标明来源。缺失用量为 null，失败或取消仍记录估算、状态、错误类型和耗时；不能将缺失数据当成零。服务商未报告缓存且宿主字段为 0 时，也不能断言服务端没有缓存。

主模型通过原生 Agent／工具钩子读取本轮原生 Runner 统计，每个可观察模型步骤写入 `scope=native_step` 的增量记录，多工具共用的一次模型请求不会重复计算；辅助模型为 `scope=call`。原生 Runner 注册表仅只读访问，集中在宿主接入模块，不替换 Provider、Runner 或全局日志方法。宿主内部重试、工具参数补全和原生压缩模型没有相同的逐次公开统计，日志不宣称覆盖这些内部调用；统计只覆盖 Humanization 管理的回复及其辅助调用。

凭据字段、常见密钥形式会脱敏，媒体二进制内容省略；调试日志仍包含聊天、提示词及工具文本，不属于可直接公开的数据。设为 0 的文件不自动清理，排查结束后可关闭调试并自行归档。日志及运行数据库不应提交到 Git。

日志通过统一工具类分流，控制台使用 AstrBot 提供的插件 logger，文件批量异步写入；不调整全局 handler，不影响宿主及其他插件日志。文件无法写入时仅向宿主报告一次错误类型，即使当前是调试模式。卸载与重载时等待待写记录完成并关闭写入任务。

## 管理指令

控制面板“管理指令”默认关闭。启用后仅 AstrBot 配置中的管理员可以使用；普通群管理员不会因此获得权限。非管理员及开关关闭时 `/hum` 消息保持静默，不回落到默认 LLM，也不作为 Humanization 的聊天资料。使用以下指令时，宿主唤醒前缀需包含 `/`；如果同时配置空前缀，须将 `/` 放在空前缀前，确保原生指令解析能去除斜线。配置 `/` 仍可观察普通群聊。

| 指令 | 使用位置 | 行为 |
| --- | --- | --- |
| `/hum info [UMO]` | 管理员群聊／私聊 | 查询当前或指定会话的 Recorder 记录数量、日记版本和进度、辅助模型及查询时间 |
| `/hum clear log` | 管理员私聊 | 清空 `runtime.log`，控制台记录结果，回复 `done` 或错误 |
| `/hum clear dev_log` | 管理员私聊 | 清空 `dev.log`；也接受用户指定的 `/hum claer dev_log` 拼写 |
| `/hum reset_data all [UMO]` | 无 UMO 时管理员群聊／私聊；指定 UMO 时仅私聊 | 确认后清空目标插件会话的原始聊天、全部日记及回复记录，重置进度和计数 |
| `/hum reset_data today [UMO]` | 同上 | 确认后清空目标的全部原始聊天及回复记录，只删除请求当日的日记，保留此前日记 |

`[UMO]` 表示可选参数，省略时操作当前会话；填写时替换为 `/sid` 查到的实际 UMO，不输入方括号。

`/hum info` 使用管理指令开关和 AstrBot 管理员权限，无需确认；当前会话和指定会话都可以在群聊或私聊查询。首行显示 `[群聊/私聊]会话名 : UMO`，名称优先使用宿主保存的别名，再使用自动名称，没有名称时显示群号或用户号。群内成员隔离 UMO 查询整群记录，首行使用整群 UMO。已有数据即使当前不在启用范围内也可查询；没有消息和日记时，告知会话无记录或会话未启用插件。仅查询元数据，不输出聊天或日记正文，不调用模型，不将查询指令／回复计入 Recorder，也不改变待确认的重置请求。

有记录时按以下六行输出（示例）：

```text
[群聊]测试群 : onebot:GroupMessage:123456
聊天记录：500/128（上限/已有条数）
现行日记版本：2026-10-14@seq100（版本生成时间：2026-10-14 18:30:00 +0800）；日记总数：2；摘要进度：50/28（触发条数/待总结新消息）
Recorder 模型：recorder-model（recorder-provider-id）
Controller 模型：controller-model（controller-provider-id）
查询时间：2026-10-14 19:00:00 +0800
```

已有条数直接统计当前数据库保留的消息行，包含机器人气泡；摘要进度中的“待总结新消息”使用现有 `human_count - summarized_count`，表示尚未总结的新增入站消息数，两者单位不同。现行日记选取最近日期的一篇，以日期和 `through_seq` 标识该版本，显示数据库记录的 `updated_at` 作为版本生成时间；不把它当作日记首次创建时间，不额外保存每次修改前的版本快照。日记总数统计包含话题的全部日期，不受模型读取窗口限制；只有空变更或缺口元数据的日期不计入日记总数。模型名称通过宿主接口读取当前配置的两个辅助模型，未配置或未加载时如实标注；查询时间与日记时间均使用插件配置时区。

重置请求必须由同一管理员在同一会话 60 秒内完整输入 `/hum IClearKnowWhatIDoingNow` 确认，超时不执行；新请求覆盖本人在该会话的旧请求，确认不可重复使用。请求当日按插件配置时区计算，确认跨午夜也按提示中明确的日期删除。

例如私聊发送 `/hum reset_data all onebot:GroupMessage:123456`，再在该私聊内确认，就会重置目标群，而非管理员的私聊。指定目标须能定位到已有 Humanization 记录或保留日记，当前是否启用不影响定位；格式错误、未知目标及在群聊中指定 UMO 均不创建请求，并取消本人同一发起会话中的旧请求。群成员隔离 UMO 也会重置整个群。

群内重置按整群执行，即使宿主按成员隔离 UMO。重置会停止该群／私聊正在执行的 Humanization 回复，防止旧事件再次启动；正在生成的本会话摘要会取消，随后恢复摘要任务。并通过 AstrBot 原生接口将对应会话切换到空白对话，保留旧对话及原有的人格选择；群内已有的成员隔离路由也一并切换。重置不清空其他群／私聊的数据或日志。此前日期的日记在 `today` 重置后仍可作为观察资料使用。

日志清空在写入队列中依次执行，会等待较早记录完成，避免旧记录被补写回来；后续新日志可以继续写入。数据删除在插件 SQLite 内使用事务，原生对话切换属于另一存储，失败时返回错误并记录原因，不宣称跨存储完全原子。命令执行结果使用原生发送流程；未进行真实平台管理指令联调。

## 危险操作区

插件配置最底部提供“清除所有会话数据”。官方配置控件没有通用操作按钮，因此使用操作开关和条件显示的确认文本框：开启开关，完整输入 `CLEAR_ALL_HUMANIZATION_DATA`，再保存。保存重载时执行一次；执行前先持久化关闭开关、清空确认文字，避免后续重载重复执行。确认文字错误时取消，配置无法保存时不会删除；执行失败后也不会自动再次尝试，详情见日志。

此操作不依赖 `/hum` 开关，清空全部已记录的 Humanization 会话，包括当前未启用会话及 `today` 重置后仅剩历史日记的会话。取消正在执行的回复、摘要和待调度消息，清空聊天／日记／回复表及进度、计数、调度状态，并通过原生接口给对应主模型新建空白对话，群成员隔离路由一并切换；原生旧对话保留。辅助模型本身不维护聊天 session，相关上下文来自被清除的记录及日记。数据库文件和表结构、日志文件保留。SQLite 与原生会话库是独立存储，发生错误时可能已完成部分会话切换或清除，不保证全局跨库原子性。

## 开发与验证

`main.py` 只注册生命周期和事件；业务代码位于 `core/`；`utils/` 扁平存放专职运行时工具类；测试位于 `test/`。

在具备当前 AstrBot 依赖的 Python 环境中运行：

```text
python -B -m pytest test -q -p no:cacheprovider -o asyncio_mode=auto
python -B -m ruff check main.py core utils test --no-cache
python -B -m ruff format main.py core utils test --no-cache --check
```

测试先将 `ASTRBOT_ROOT` 指向独立临时目录，不访问真实会话数据、不调用真实模型或发送真实群消息。临时产物保留供检查，不执行批量目录清理。测试依赖 `pytest`、`pytest-asyncio`；它们不属于插件运行时依赖。

测试覆盖原生 Pipeline 调度、插件加载与配置、媒体标签、滚动存储、摘要游标、主动发言取消，以及 B 方案的原生装饰／发送、工具循环、发送后钩子和缓存释放。消息调度另使用固定时钟验证小数额度、有限等待、合并、冷却／退避、时段变化、强制提及、新消息并发及旧事件失效；原生接入验证延迟事件不重复入站记录，并保留引用、TTS、文转图、分段和工具循环。TTS、文转图、模型及平台使用测试替身，实际装饰与发送阶段使用宿主实现；尚未进行真实模型与 OneBot 群聊联调。

观察期与重置测试覆盖 49／50 条边界、Recorder 入库过滤／去重／滚动、群整体及私聊独立、必回复与主动发言、指令目标及确认身份、保留历史日记的重复重置、旧回复／摘要／消息失效，以及面板操作的确认、保存失败和仅执行一次。

插件不声明或安装额外运行依赖。数据库使用 AstrBot 已有的 `aiosqlite`，其余逻辑使用标准库和宿主接口；时区使用标准库 `zoneinfo`。Windows 时区数据由宿主已有的 APScheduler → tzlocal 依赖链提供。

普通消息仍须经过宿主白名单、限流和安全检查；被前置流程拦截的消息无法由此插件记录。统一使用宿主原生请求收集器和临时内容块接口。更换 AstrBot 版本时应重新运行接入契约测试。
